🏛️ Architecture, System Design & Interview Justifications
Pattern

1. Asynchronous Ingestion & Decoupled Execution

Bulk generation requests (e.g. 500+ recipients) would inevitably exceed HTTP gateway timeouts (typically 30 seconds) if executed synchronously. We decouple request intake from certificate generation: the API validates the envelope, saves initial records as PENDING, immediately returns 202 Accepted with a job_id and polling URL, and executes generation asynchronously in the background.

Fault Tolerance

2. Recipient-Level Fault Isolation

A single corrupted email or unhandled character set in recipient #15 must never abort the remaining 999 valid certificates. Each recipient is wrapped in an individual error boundary inside the worker loop. Unprocessable records are marked FAILED with a detailed error trace, while valid records succeed with SUCCESS, transitioning the aggregate job status cleanly to PARTIALLY_COMPLETED.

Rendering Engine

3. High-Resolution Dual Export (Pillow 300 DPI)

Instead of relying on fragile external webkit/headless browser binaries (which are prone to memory bloat and platform rendering differences), we utilize pure-Python Pillow at 300 DPI (2000×1414 pixels). It exports both print-ready PDFs and crisp PNGs simultaneously while dynamically generating and pasting a scannable QR verification code.

Production Scaling

4. Production Scalability to 100k+ Certs/Day

The architecture is intentionally designed for horizontal scalability:
• Queue: Easily replace FastAPI BackgroundTasks with Celery / ARQ + Redis across multiple worker nodes.
• Storage: Local directory storage can be swapped with AWS S3 / Google Cloud Storage using signed URLs.
• Database: SQLite database can be swapped to PostgreSQL simply by changing the DATABASE_URL environment variable.
